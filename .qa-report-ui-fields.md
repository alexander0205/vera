## A) Root cause — "Monto Total: campo requerido" and "Indicador de Facturación: requerido en ítem N"

### A.1 What the validator sees

`NuevaFacturaForm.tsx:497-510` invokes `validateEcf(tipoEcf, payload, { context: { tipoPago, ncfModificado, montoTotal: totales.total, rncComprador } })` with the same `payload` that is later POSTed to `/api/ecf/emitir`.

That `payload` is built by `buildPayload()` in `app/(dashboard)/dashboard/facturas/nueva/utils/buildPayload.ts:52-112`. Inspecting the returned object:

- No `montoTotal` key is ever set on the payload. Subtotal/ITBIS/total are computed by `calcularTotales()` (`utils/calculos.ts:22-42`) and only stored in component state (`totales`).
- Each item only has these keys (`utils/buildPayload.ts:70-78`): `nombreItem`, `descripcionItem`, `cantidadItem`, `precioUnitarioItem`, `descuentoMonto`, `tasaItbis`, `indicadorBienoServicio`. **No `indicadorFacturacion`** and **no `montoItem`**.

### A.2 What the schemas require

Every tipo (31, 32, 33, 34, 41, 43, 44, 45, 46, 47) lists `montoTotal` as `REQUIRED` (schemas, section `Totales`, payloadKey `montoTotal`, e.g. `lib/factura/validator/schemas/31.json` — `Monto Total` DGII #110). Every tipo also lists `items[].indicadorFacturacion` as `REQUIRED` (DGII #4, section `Items`, valores `[0,1,2,3,4]`). `items[].montoItem` is also REQUIRED across all tipos.

### A.3 How the rule fires

In `lib/factura/validator/index.ts:258-271` for top-level REQUIRED fields:

```ts
const value = getTopLevelValue(payload, campo.payloadKey);
const present = isPresent(value);

if (campo.obligatoriedad === 'REQUIRED') {
  if (!present) {
    errors.push(makeError(campo, 'REQUIRED_MISSING', `${campo.nombre}: campo requerido`));
    continue;
  }
}
```

→ `montoTotal` is missing on payload, so it is flagged. The `context.montoTotal` provided in the call (`NuevaFacturaForm.tsx:507`) is only consulted by `resolveMontoTotal()` in `conditional-rules.ts:65-74` — that function is used **only** by the E32-threshold CONDITIONAL rules for `rncComprador / razonSocialComprador / identificadorExtranjero`. It is **not** consulted for the top-level REQUIRED check of `montoTotal` itself.

For item-level fields, `index.ts:219-237`:

```ts
items.forEach((item, idx) => {
  const value = getItemValue(item, itemKey);
  const present = isPresent(value);

  if (campo.obligatoriedad === 'REQUIRED' && !present) {
    errors.push(makeError(campo, 'REQUIRED_MISSING',
      `${campo.nombre}: requerido en ítem ${idx + 1}`, undefined, idx));
    return;
  }
  ...
});
```

→ Items lack `indicadorFacturacion` AND `montoItem` → each item raises a `REQUIRED_MISSING`. Only the first 3 errors are shown (`NuevaFacturaForm.tsx:512`), which is why the user sees "Monto Total" + the first two items (and the per-item `montoItem` error gets cropped).

### A.4 Why this only manifests now

`emision-mapper.ts:124-129` (`tasaToIndicador`) and the server-side mapper compute `indicadorFacturacion` and `montoItem` server-side. The client validator was added recently and runs against the raw form payload that has never carried these derived fields. The server still computes them correctly, so the underlying submission succeeds when the validator is bypassed.

### A.5 Recommended fix (recommended: Option A — augment payload before validation)

Add a "validation view" of the payload that includes the derived fields. Smallest patch, no schema changes:

`NuevaFacturaForm.tsx:500-510` — change to:

```ts
if (modo === 'emitir') {
  try {
    const payload = buildPayload('emitir');
    const validationPayload = {
      ...payload,
      montoTotal: totales.total,
      items: (payload.items ?? []).map((it: any) => ({
        ...it,
        indicadorFacturacion: tasaToIndicador(it.tasaItbis),
        montoItem: round2(
          (it.cantidadItem * it.precioUnitarioItem - (it.descuentoMonto ?? 0))
          * (1 + (it.tasaItbis ?? 0))
        ),
      })),
    };
    const result = validateEcf(tipoEcf, validationPayload, {
      context: { tipoPago: plazoActual?.dgiiTipo, ncfModificado: ncfModificado || undefined, montoTotal: totales.total, rncComprador: payload.rncComprador as string | undefined },
    });
    ...
  }
}
```

Where `tasaToIndicador` is either imported from a shared helper (preferred — move it out of `lib/ecf-api/emision-mapper.ts:124`) or re-implemented inline. The current `tasaToIndicador` lives only in the server-side mapper and is not exported.

Option B (lower fidelity): skip those fields client-side and rely on server validation. Cheaper but throws away the value-add of running the validator client-side, and re-introduces the "submit-then-fail" UX the validator was meant to prevent.

Option C (most thorough but largest change): teach the validator to derive these. Add a "derivation layer" in `validator/index.ts` that runs before REQUIRED checks. This couples the validator to business rules and is the wrong direction.

→ **Adopt Option A.** It is mechanical, fixes the error today, and the validator stays pure.

Also: `lib/factura/validator/conditional-rules.ts:87-102` already reads `items[].indicadorFacturacion` for `hasItbisItems` — once items carry the derived value, the existing `indicadorMontoGravado` CONDITIONAL rule (`indicadorMontoGravado is required cuando existen ítems gravados con ITBIS`) will start firing on the client too. Today it silently never fires because items lack the key. See section C.

### B.3 UI fields that don't drive an `esCampoRequerido` lookup

Most asterisks in the form are hardcoded (`<span className="text-red-500">*</span>`). Only `tipoIngresos` uses `esCampoRequerido(tipoEcf, 'tipoIngresos')` (`DetallesSection.tsx:82`) and `ClienteSection.tsx:76` uses `getCampoHint` for the RNC tooltip. Everything else falls back to the legacy `regla` map (`lib/ecf/types.ts:46-167`) which is duplicated truth (e.g. `requiereRncComprador`). This is a maintenance hazard — when the schema obligatoriedad changes, the asterisks won't follow.

## C) Conditional-rules coverage gaps (`lib/factura/validator/conditional-rules.ts`)

Rules registered today (file confirms `_ruleCount` = 36):

| Field | Tipos covered | Predicate | Match with schema |
|---|---|---|---|
| `fechaLimitePago` | 31, 32, 33, 34, 41, 44, 45, 46 | `tipoPago === 2` | OK |
| `fechaNCFModificado` | 31, 32, 33, 34, 41, 43, 44, 45, 46, 47 | `ncfModificado` present | OK |
| `codigoModificacion` | 31, 32, 33, 34, 41, 43, 44, 45, 46, 47 | `ncfModificado` present | OK |
| `indicadorMontoGravado` | 31, 32, 33, 34, 41, 45 | any item with `indicadorFacturacion ∈ {1,2,3}` | OK conceptually, but **never fires today** because items lack `indicadorFacturacion` (root cause). Will start firing once Option A is applied. |
| `totalISRRetencion` | 31, 33, 34, 41, 47 | any item with `montoISRRetenido > 0` | OK; ineffective because no item-level UI |
| `rncComprador` / `razonSocialComprador` / `identificadorExtranjero` | 32, 33, 34, 44, 46 | `montoTotal ≥ 250000` (extra `rnc empty` for `identificadorExtranjero`) | Reads `ctx.montoTotal` first, falls back to `payload.montoTotal`. Form passes `ctx.montoTotal` (`NuevaFacturaForm.tsx:507`), so works even without `payload.montoTotal`. OK. |

Gaps found:

1. **`indicadorNotaCredito` for tipo 34** — schema marks it REQUIRED, not CONDITIONAL. No rule needed. But form does not collect it and `buildPayload` does not emit it. Either:
   - derive it client-side (`computeIndicadorNotaCredito` from `emision-mapper.ts:193`) before validation, OR
   - add a UI input (toggle: "Más de 30 días desde la factura original?").

2. **`fechaLimitePago` is NOT registered for tipo 47**, but schema 47 marks `fechaLimitePago` as `OPTIONAL` for that tipo (not CONDITIONAL). The current omission is correct — but verify with the live schema.

3. **`identificadorExtranjero` rule references `rncComprador` only, not `rncProveedor`** — for tipo 41 the schema uses `rncProveedor` as the buyer/supplier identifier. Rule does not apply (tipo 41 not in list `['32','33','34','44','46']`). OK.

4. **`montoNoFacturable` (C)** — no rule. Schemas don't include a `condicion` string, so leaving it un-checked is fine (it stays optional from validator's POV). Just be aware that if business needs to enforce it later, no rule exists.

5. **Item-level CONDITIONAL fields are never enforced.** `index.ts:250-251` explicitly notes "CONDITIONAL on item-level fields: no per-item predicate today." So `items[].indicadorAgenteRetencionoPercepcion`, `items[].montoISRRetenido`, `items[].montoITBISRetenido` are silently un-validated for tipos where they are CONDITIONAL (31, 33, 34, 41 — but for 41 and 47 the schema marks them REQUIRED, which IS enforced).

6. **`rncOtroContribuyente`** — CONDITIONAL across all 10 tipos but no rule registered. The DGII norma triggers this when a third RNC is involved (e.g. an intermediate facturador). No UI either. Acceptable to leave un-enforced until a use-case appears.

## D) Suggested code changes (read-only — for the implementer)

### D.1 Fix client validator misfire (root cause)

`app/(dashboard)/dashboard/facturas/nueva/NuevaFacturaForm.tsx:500-514`

Before:
```ts
if (modo === 'emitir') {
  try {
    const payload = buildPayload('emitir');
    const result = validateEcf(tipoEcf, payload, {
      context: {
        tipoPago: plazoActual?.dgiiTipo,
        ncfModificado: ncfModificado || undefined,
        montoTotal: totales.total,
        rncComprador: payload.rncComprador,
      },
    });
    if (!result.ok && result.errors.length > 0) {
      setError(result.errors.slice(0, 3).map(e => `${e.nombre}: ${e.message}`).join('; '));
      return;
    }
  } catch (e) { console.warn('[validator] fallo silencioso:', e); }
}
```

After (sketch):
```ts
if (modo === 'emitir') {
  try {
    const payload = buildPayload('emitir');

    // Derived fields the server-side mapper computes;
    // mirror them here so the schema-driven validator can see them.
    const validationPayload = {
      ...payload,
      montoTotal: totales.total,
      // tipo 34: derive indicadorNotaCredito (0 ≤ 30d, 1 > 30d)
      ...(tipoEcf === '34'
        ? { indicadorNotaCredito: computeIndicadorNotaCredito(fechaNcfModificado) }
        : {}),
      items: (payload.items ?? []).map((it) => ({
        ...it,
        indicadorFacturacion: tasaToIndicador(it.tasaItbis),
        montoItem: computeMontoItemFromPayloadItem(it),
        ...(tipoEcf === '41' || tipoEcf === '47'
          ? { indicadorAgenteRetencionoPercepcion: 1 /* default, until UI exists */ }
          : {}),
      })),
    };

    const result = validateEcf(tipoEcf, validationPayload, {
      context: {
        tipoPago: plazoActual?.dgiiTipo,
        ncfModificado: ncfModificado || undefined,
        montoTotal: totales.total,
        rncComprador: payload.rncComprador as string | undefined,
      },
    });
    if (!result.ok && result.errors.length > 0) {
      setError(result.errors.slice(0, 3).map(e => `${e.nombre}: ${e.message}`).join('; '));
      return;
    }
  } catch (e) { console.warn('[validator] fallo silencioso:', e); }
}
```

Helpers to extract / share between client and server-mapper:

- `tasaToIndicador(tasa?: number): number` — currently private at `lib/ecf-api/emision-mapper.ts:124-129`. Move to a shared module (e.g. `lib/ecf/derivations.ts` or extend `app/(dashboard)/dashboard/facturas/nueva/utils/calculos.ts`) and import from both sides.
- `computeIndicadorNotaCredito` — same, currently at `lib/ecf-api/emision-mapper.ts:193-199`.
- `computeMontoItemFromPayloadItem` — new; matches the server's rounding rule (use `round2` from `utils/calculos.ts:3-5`).

### D.2 Tipo 41 — emit `rncProveedor` / `razonSocialProveedor`

`app/(dashboard)/dashboard/facturas/nueva/utils/buildPayload.ts:56-58`

The current code always writes `rncComprador` / `razonSocialComprador`. For tipo 41, the schema's REQUIRED keys are `rncProveedor` and `razonSocialProveedor` (per `lib/factura/validator/schemas/41.json`). Either:

- (a) Re-key in `buildPayload` when `tipoEcf === '41'`, OR
- (b) Re-key only inside `validationPayload` (Option A pattern), OR
- (c) Centralize: have one canonical buyer-identity block that the validator normalizes.

Simplest fix is (b) — re-key locally for validation. The server mapper already handles the rename.

### D.3 Tipo 43 — strip FORBIDDEN keys before validating

For tipo 43, the schema lists 25 FORBIDDEN fields including `tipoPago`, `rncComprador`, `razonSocialComprador`, `emailComprador`, `tipoIngresos`, `fechaLimitePago`. `buildPayload` always emits `tipoPago` (`buildPayload.ts:59`). Either:

- Conditionally omit these in `buildPayload` when tipo === '43', OR
- Drop them in the `validationPayload` view.

Recommended: handle in the same Option-A "validation view" so server contract is untouched.

### D.4 Drive asterisks from `esCampoRequerido` everywhere

The schema is the source of truth, but only `DetallesSection.tsx:82` uses it. Convert hardcoded asterisks to:

```tsx
<RequiredMark tipo={tipoEcf} field="rncComprador" ctx={validationCtx} />
```

so the form automatically follows future schema edits. Affected sections: `ClienteSection.tsx`, `DetallesSection.tsx` (fecha, NCF mod block, plazo), `ItemsTable.tsx`.
