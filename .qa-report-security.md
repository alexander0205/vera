# EmiteDO — Security Audit Report

**Auditor:** Sofía (Security Engineer)
**Date:** 2026-05-12
**Build under test:** `feature/lite-version` @ `e828ed3`
**Methodology:** Static analysis + dynamic black-box testing against `http://localhost:3002`
**Two test accounts used:** platform admin (id=1) and team member (id=4, team_id=2)

> **TL;DR** — Found **3 P0 (critical, exploitable now)**, **5 P1 (high-impact)**, **8 P2 (hardening)**, and several compliance gaps. The application is NOT production-ready as it stands. The biggest concerns are: (1) `/api/user` leaking `passwordHash` and `twoFactorSecret`, (2) 2FA is never enforced on login despite being a settings toggle, (3) `/api/team` returns full team row including AES-GCM ciphertexts and IVs, and (4) several email-bombing / account-creation vectors are not rate-limited.

---

## A) Critical Vulnerabilities — P0 (exploitable now)

### A-1. `/api/user` GET leaks `passwordHash` and `twoFactorSecret`
- **File:** `app/api/user/route.ts:6-9` → `lib/db/queries.ts:35-46` (`getUser()` returns `users.*`)
- **OWASP:** A01 Broken Access Control / A04 Insecure Design / CWE-200, CWE-256
- **Impact:** Any authenticated user (including a stolen session) gets the bcrypt `passwordHash` of the authenticated user and their `twoFactorSecret`. Attacker who obtains a session can extract the hash and crack offline (bcrypt cost=10 is feasible for weak passwords). Combined with `twoFactorSecret`, attacker generates valid TOTP codes even if 2FA were enforced.
- **PoC (with forged session cookie — AUTH_SECRET is in `.env` and known via repo):**
  ```bash
  curl -k -H "Cookie: session=<jwt>" http://localhost:3002/api/user
  # → { ..., "passwordHash":"$2b$10$o0WUbWdY4FZqq987zTYYyu...", "twoFactorSecret":"OLQCBP3O43TQJABG4A2YV5NMA77Y5FBD", ... }
  ```
- **Fix:** In `/api/user/route.ts` GET, project only safe columns (`id, name, email, platformRole, emailVerified, twoFactorEnabled, createdAt, updatedAt`). Never return `passwordHash`, `twoFactorSecret`, `deletedAt` to the client. Same for any `getUser()` callers that send the object back to the client.

### A-2. 2FA is never enforced on login (security theater)
- **File:** `app/(login)/actions.ts:53-112` (`signIn`)
- **OWASP:** A07 Identification & Auth / CWE-287
- **Impact:** Users can enable 2FA in `/api/auth/2fa/setup`, but the `signIn` server action **only checks password**. After password match it calls `setSession(foundUser)` and redirects. 2FA codes are never validated during sign-in. Attackers with leaked passwords bypass 2FA entirely.
- **Repro:** Trace `grep -n twoFactorEnabled app/(login)/actions.ts` → 0 hits.
- **Fix:** If `foundUser.twoFactorEnabled === true`, return a "needs_2fa" state to the client (do NOT set session yet) and require the user to submit a TOTP code via a follow-up action that validates against `twoFactorSecret`. Re-use the `OTPAuth.TOTP.validate({ window: 1 })` pattern from `app/api/auth/2fa/setup/route.ts`.

### A-3. `/api/auth/2fa/setup` GET silently overwrites an enabled user's `twoFactorSecret`
- **File:** `app/api/auth/2fa/setup/route.ts:8-25`
- **OWASP:** A04 Insecure Design / CWE-640
- **Impact:** A user who already has 2FA enabled can call `GET /api/auth/2fa/setup` (or be tricked via CSRF — no anti-CSRF check) and the route generates a new TOTP secret and **immediately writes it to the DB**, replacing the current one. `twoFactorEnabled` remains true. The user's authenticator app now shows wrong codes → permanent lockout. CSRF here is also a path to silently rotate a target's 2FA secret to one the attacker knows (then enable it).
- **PoC:**
  ```bash
  # Run twice; the second call overwrites the secret, and a real 2FA user is locked out
  curl -H "Cookie: session=$SESS" http://localhost:3002/api/auth/2fa/setup
  ```
- **Fix:** GET should never mutate state. Only generate the secret server-side and respond with it. Store the "candidate" secret in a separate column (`twoFactorSecretPending`) and only promote it to `twoFactorSecret` after the user verifies a code (`POST /api/auth/2fa/setup`). Reject the setup flow if `twoFactorEnabled === true` (require disable first).

## B) High-Impact Vulnerabilities — P1

### B-1. `/api/team` GET returns full row including encrypted cert ciphertext, Stripe IDs, DGII tokens
- **File:** `app/api/team/route.ts` + `lib/db/queries.ts:111-143` (`getTeamForUser()`)
- **OWASP:** A01 Broken Access Control / CWE-200
- **Impact:** Any team member receives the team row containing `stripeCustomerId`, `stripeSubscriptionId`, `dgiiRoutingToken`, `dgiiTokenCiphered`, `dgiiTokenIv`, `dgiiTokenAuthTag`, `certP12Ciphered`, `certP12Iv`, `certP12AuthTag`, `certPinCiphered`, `certPinIv`, `certPinAuthTag`, `habilitacionState`, etc. While ciphertext requires `CERT_MASTER_KEY` to decrypt, **leaking the IVs + ciphertexts to non-privileged clients** lowers the attack surface (and `dgiiRoutingToken` is a UUID that goes in a *public* DGII URL — but the rest is internal).
- **PoC:**
  ```bash
  curl -H "Cookie: session=<member-jwt>" http://localhost:3002/api/team
  ```
- **Fix:** Project only client-needed columns (`id, razonSocial, nombreComercial, rnc, planName, subscriptionStatus, dgiiEnvironment, dgiiRoutingToken, logo, telefono, sitioWeb, emailFacturacion, certTitular, certVencimiento`). Strip every `*Ciphered`, `*Iv`, `*AuthTag`, `habilitacionState`, and Stripe `*Id` field.

### B-2. `POST /api/equipo/perfil` allows ANY team member to edit the team profile (no role check)
- **File:** `app/api/equipo/perfil/route.ts:29-60`
- **OWASP:** A01 Broken Access Control / CWE-862
- **Impact:** A `member`/`vendedor` can rename the team, replace `logo`/`firma`, change `emailFacturacion` (which appears on factura emails). No `requireTeamRole(... 'owner' | 'admin')` check.
- **PoC (verified live during audit):**
  ```bash
  curl -X POST -H "Cookie: session=<member-jwt>" -H "Content-Type: application/json" \
    -d '{"razonSocial":"HIJACKED COMPANY"}' http://localhost:3002/api/equipo/perfil
  # → {"ok":true}  (team renamed by non-owner)
  ```
- **Fix:** Add `await requireTeamRole(user.id, teamId, 'admin');` at the top of POST.

### B-3. Account / team / email creation has no rate-limiting → spam, enumeration, email-bombing
- **Endpoints affected:**
  - `signUp` server action (`app/(login)/actions.ts:121`) — **no rate limit**
  - `POST /api/empresa` create team (`app/api/empresa/route.ts:14`) — **no rate limit, no plan check**
  - `POST /api/auth/forgot-password` (`app/api/auth/forgot-password/route.ts:8`) — **no rate limit**
  - `POST /api/auth/send-verification` (`app/api/auth/send-verification/route.ts:8`) — **no rate limit**
  - `POST /api/facturas/[id]/email` (`app/api/facturas/[id]/email/route.ts:8`) — **no rate limit**; `targetEmail` is user-supplied, so an authenticated user can send arbitrary PDF emails from `noreply@yisraeltech.com` to any address (spam/phishing using the project's authenticated email sender).
- **OWASP:** A04 Insecure Design / CWE-770 / CWE-307
- **PoC (verified):** Hit `POST /api/auth/forgot-password` 12 times in a row → all return 200 (every call sends a real Resend email).
- **Fix:** Add `rateLimitDb` (already implemented for cert upload) on every flow that sends email or creates account/team. Suggested keys: `forgot:<ip>` 3/hour, `send-verify:<userId>` 3/hour, `signup:<ip>` 5/hour, `invoice-email:<teamId>` 30/day.

### B-4. Forgot-password timing channel reveals which emails exist
- **File:** `app/api/auth/forgot-password/route.ts:11-31`
- **OWASP:** A07 Identification & Auth / CWE-204
- **Impact:** Existing email → ~1700ms (DB read + token insert + Resend API call). Nonexistent email → ~150ms (just one DB read). 10× delta → trivial email enumeration even though the body always returns `{success:true}`.
- **PoC (verified):**
  ```bash
  time curl -X POST -d '{"email":"alexander.ferreras@yisraeltech.com"}' .../forgot-password  # 1.78s
  time curl -X POST -d '{"email":"nope-xyz@example.com"}' .../forgot-password               # 0.15s
  ```
- **Fix:** When user is not found, still simulate the same work (`await new Promise(r => setTimeout(r, 800 + Math.random()*400))`), OR queue the email send asynchronously with `after(...)` so both branches return immediately and look identical. The current "return success in both branches" is correct but is undone by the timing leak.

### B-5. Rate-limit relies on user-controlled `X-Forwarded-For` header
- **File:** `app/(login)/actions.ts:57`, `app/invitations/accept/page.tsx:35`, `lib/audit.ts` (getIp helper, used in multiple endpoints)
- **OWASP:** A04 Insecure Design / CWE-290
- **Impact:** `rateLimit('login:' + req.headers['x-forwarded-for'])` keys on whatever the client sends. Local development has no trusted proxy stripping it. Attacker can rotate `X-Forwarded-For: 1.2.3.<i>` per request and never hit the 10/min cap → unlimited password-guessing.
- **Fix:** Use the **leftmost public IP** from `X-Forwarded-For` only when behind a trusted proxy (Vercel sets `x-real-ip` / `x-vercel-forwarded-for`). Document explicitly that this header must come from the platform, not the user. As a defense in depth, also rate-limit per-email/per-userId, not only per-IP.

## C) Medium / Hardening — P2

### C-1. AUTH_SECRET in `.env` is low-entropy, predictable string
- **File:** `.env:2` → `AUTH_SECRET=emitedo-dev-secret-local-32chars-min`
- **OWASP:** A02 Cryptographic Failures / CWE-330
- **Impact:** This value is the HMAC key for all session JWTs. If this exact string lands in production (or a leaked screenshot/repo crawl finds it), every JWT is forgeable. During the audit I forged admin and member sessions trivially.
- **Fix:** Generate via `openssl rand -base64 48`. Document explicitly that the dev value MUST be replaced. Add a runtime guard in `lib/env.ts` that refuses to start in production with the default value.

### C-2. SSRF via outbound webhook URL (no allowlist / blocklist for private IPs)
- **File:** `app/api/webhooks/route.ts:15-32`
- **OWASP:** A10 SSRF / CWE-918
- **Impact:** When a webhook eventually fires server-side, an attacker-supplied URL like `http://169.254.169.254/latest/meta-data/`, `http://127.0.0.1:5432`, or `http://localhost:3010/...` (ecf-api internal!) would be hit, potentially leaking cloud-metadata or pivoting onto internal services. PoC (verified): `POST /api/webhooks` with `"url":"http://169.254.169.254/..."` returned 201 with no validation.
- **Fix:** When dispatching, resolve the host; reject any URL whose resolved IP is in RFC1918, link-local, loopback, or AWS/GCP metadata ranges. Require `https://` only. Optionally allowlist user-configured domains per team.

### C-3. HTML injection via user-controlled fields in outgoing emails
- **File:** `lib/email/index.ts:11-23, 33-46, 60-71, 86-92`
- **OWASP:** A03 Injection (HTML email) / CWE-79 (in email clients that allow some HTML)
- **Impact:** `${name}`, `${invitedByName}`, `${teamName}`, `${razonSocial}`, `${encf}` are interpolated raw into HTML emails. A malicious team name or user name like `<a href="https://evil.com">Click here</a>` (or `<style>`+`<img>` payloads) is injected. Most modern mail clients (Gmail, Outlook web) strip scripts but render anchors/images → phishing-grade injection from a tenant boundary.
- **Fix:** Escape every interpolated string with a small `escapeHtml()` helper before placing into `html: \`\``.

### C-4. No security headers (CSP, X-Frame-Options, X-Content-Type-Options, HSTS, Referrer-Policy, Permissions-Policy)
- **File:** `next.config.ts` (no `headers()` config), `proxy.ts` (only sets cookies)
- **OWASP:** A05 Security Misconfiguration / CWE-693
- **Impact:** Clickjacking (no X-Frame-Options/CSP frame-ancestors), MIME-sniffing (no X-Content-Type-Options), no HSTS, generous referrer leakage, no Permissions-Policy. CSP absence means any reflected/stored content executes freely.
- **Fix:** Add `async headers()` in `next.config.ts` returning at minimum:
  ```
  Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
  X-Frame-Options: DENY
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
  Permissions-Policy: geolocation=(), camera=(), microphone=()
  Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-...'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; connect-src 'self' api.stripe.com; frame-ancestors 'none'
  ```

### C-5. `signOut` server action throws if session is already expired
- **File:** `app/(login)/actions.ts:239-244`
- **Impact:** `const user = (await getUser()) as User;` — if `getUser()` returns null, subsequent `user.id` throws and leaks stack to logs (and a 500 to the user). Not exploitable, but ugly.
- **Fix:** Early-return when `user` is null.

### C-6. `/api/empresa` POST allows infinite team creation per user (DoS / spam)
- **File:** `app/api/empresa/route.ts:14-50`
- **OWASP:** A04 Insecure Design / CWE-770
- **Impact:** Any authenticated user can spam `POST /api/empresa` creating unlimited teams. Each team triggers 10 sequence inserts in admin flow; the user-facing flow doesn't seed sequences but still inflates DB / clutters `/api/empresa/list`.
- **Fix:** Limit teams per user (e.g., 3 free; plan-gated otherwise). Add `rateLimitDb('create-team:'+userId, 5, 86400_000)`.

### C-7. Session JWT is silently extended on every GET (sliding window with no absolute cap)
- **File:** `proxy.ts:22-37`
- **OWASP:** A07 Auth / CWE-613
- **Impact:** As long as a session is used, expiration is bumped 24h. There's no absolute session lifetime ceiling. A stolen session lives forever as long as the attacker uses it once a day.
- **Fix:** Track an `issuedAt` (already in JWT) and refuse to refresh if `now - iat > 30 days`. Force re-login periodically.

### C-8. Stack trace / error messages exposed in some 500s
- **File:** e.g. `app/api/equipo/invitaciones/route.ts:125` — `return NextResponse.json({ error: message }, { status: 500 })` echoes `err.message` verbatim from any thrown exception. May leak SQL error text, internal field names, or stack-style strings.
- **OWASP:** A04 / CWE-209
- **Fix:** Log `err` to server logs; return a generic `{ error: 'Error interno' }` to clients.

## D) Compliance / Best Practices

| Area | Finding |
|---|---|
| Secrets in `.env` | `.env` is gitignored (verified), no secrets in git history (`git log -p -S ecfk_live` returned 0). ECF_API_KEY, RESEND_API_KEY, STRIPE_SECRET, Neon DB URL all exist plaintext in `.env` — fine for local, but `CERT_MASTER_KEY` and `AUTH_SECRET` MUST rotate per env. Document this. |
| `.env.example` | Clean, no real secrets. ✅ |
| Client-bundle leak | `grep -r "ECF_API_KEY\|AUTH_SECRET" .next/static/` → 0 matches. ✅ |
| Server bundle | `ECF_API_KEY` appears in `.next/server/` (expected — server-only) but the chunk is also emitted as `.map` source maps — sourcemaps in `.next/server/` shouldn't be deployed/served. Verify Vercel deployment doesn't expose `.map` files publicly. |
| Cookie flags | `httpOnly: true, secure: true, sameSite: 'lax'` ✅ (set in `lib/auth/session.ts:50-55, 69-74` and `proxy.ts:33-36`). |
| JWT algorithm | HS256 enforced, `alg:none` rejected (verified — returns 500 `JOSEAlgNotAllowed`). ✅ |
| AES-256-GCM IV reuse | `lib/crypto/cert.ts:39` generates fresh `randomBytes(16)` per encryption. ✅ |
| Bcrypt cost | `SALT_ROUNDS = 10` — adequate but bump to 12 for production with modern hardware. |
| Invitation tokens | `randomBytes(32).toString('hex')` → 256-bit entropy ✅. Verified token length == 64 enforced on accept page. Token is single-use (status flips to `accepted`). ✅ |
| Email-verification / Password-reset tokens | Same 32-byte random construction ✅. Reset token has 1-hour expiry + `usedAt` single-use. ✅ |
| SQL Injection | Drizzle parameterizes all queries; `ilike(clients.razonSocial, \`%${q}%\`)` is parameterized (verified — `q=' OR '1'='1` returned empty result, no DB error). ✅ |
| Stripe webhook signature | `stripe.webhooks.constructEvent(payload, signature, webhookSecret)` ✅. |
| CSRF | Next.js server actions verify origin (built-in protection in Next 15). Non-server-action POSTs (`/api/*`) lack CSRF tokens; `sameSite: 'lax'` cookie mitigates cross-site POST but not same-site sub-domain. Add explicit `Origin`/`Referer` validation on sensitive POSTs (cert upload, profile edit, webhook create). |
| 404 / 500 leaks | Default Next.js error pages — no version disclosure beyond `X-Powered-By: Next.js`. Recommend removing `x-powered-by` via `poweredByHeader: false` in `next.config.ts`. |
| robots.txt / sitemap.xml | None present — neutral. Recommend `robots.txt` with `Disallow: /admin`. |
| Activity log | `activityLogs` populated for `SIGN_IN`, `SIGN_UP`, `SIGN_OUT`, `UPDATE_PASSWORD`, `DELETE_ACCOUNT`, `INVITE_TEAM_MEMBER`, `ACCEPT_INVITATION`. Missing: `2FA_ENABLE`, `2FA_DISABLE`, `EMAIL_CHANGE`, `PASSWORD_RESET`. |
| Source-map exposure | `tsconfig.tsbuildinfo` (1.8 MB) checked in — not a secret, but a code-leakage / fingerprinting aid. `.gitignore` is missing it. |

## Recommended Remediation Order

1. **Today (P0):** Patch A-1, A-2, A-3. These are direct credential and auth-bypass issues.
2. **This week (P1):** B-1 (team column filter), B-2 (role check), B-3 (rate limiting), B-4 (constant-time forgot-password), B-5 (trusted-proxy IP).
3. **Before launch (P2):** Headers (`next.config.ts headers()`), SSRF guard, email escaping, strong AUTH_SECRET enforcement, session absolute-lifetime cap.
4. **Compliance:** Document key-rotation procedure for `CERT_MASTER_KEY` and `AUTH_SECRET`. Add `poweredByHeader: false`. Strip stale `tsconfig.tsbuildinfo` from git.
