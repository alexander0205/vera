## B) Critical bugs (P0)

### B1. `GET /api/user` expone `passwordHash` y `twoFactorSecret`
- **File:** `app/api/user/route.ts:6-9`
- **Repro:** `curl -b session http://localhost:3002/api/user` devuelve el objeto user completo, incluyendo `passwordHash: "$2b$10$..."` y `twoFactorSecret`.
- **Evidence (live):**
  ```json
  {
    "id": 1,
    "name": "Alexander Ferreras",
    "email": "alexander.ferreras@yisraeltech.com",
    "passwordHash": "$2b$10$o0WUbWdY4FZqq987zTYYyuIehchBhFxRD2KUfeIjwi9c5BGsS4DOq",
    "platformRole": "admin",
    "twoFactorSecret": null,
    "twoFactorEnabled": false,
    ...
  }
  ```
- **Impacto:** Cualquier usuario autenticado puede descargar el bcrypt hash de su propia contraseña y crackearla offline. Si activan 2FA, también se expone el secret TOTP por la misma ruta.
- **Fix:** En `app/api/user/route.ts:7`, sustituir `Response.json(user)` por un `select()` explícito (id, name, email, platformRole, emailVerified, twoFactorEnabled, createdAt). Nunca devolver `passwordHash` ni `twoFactorSecret`.
- **Esfuerzo:** 5 min.

### B2. Inicio de sesión NO desafía 2FA cuando el usuario lo tiene activado
- **File:** `app/(login)/actions.ts:84-111`
- **Behavior:** El flujo `signIn` valida usuario+password, llama `setSession(foundUser)` y redirige a `/dashboard` o `/admin` sin verificar `foundUser.twoFactorEnabled`/`twoFactorSecret`.
- **Repro:** Un usuario con 2FA activo en `/dashboard/security` aún puede iniciar sesión con solo email+password.
- **Impacto:** 2FA es seguridad teatral. El endpoint `/api/auth/2fa/setup` y el panel UI hacen creer al usuario que está protegido cuando no lo está.
- **Fix:** Después del `comparePasswords`, si `foundUser.twoFactorEnabled` y `foundUser.twoFactorSecret`, NO llamar `setSession`; devolver un challenge intermedio (cookie de sesión parcial con flag `pending2fa`) y mostrar un input TOTP en `/sign-in`. Validar el código con `OTPAuth` antes de `setSession`. Patrón similar a `/api/auth/2fa/disable/route.ts`.
- **Esfuerzo:** 1.5 h.

### B3. `signUp` acepta invitaciones EXPIRADAS
- **File:** `app/(login)/actions.ts:162-193`
- **Behavior:** La query de invitación en `signUp` filtra por `token + email + status='pending'` PERO no chequea `expiresAt > now()`. El landing `/invitations/accept` sí lo hace (`app/invitations/accept/page.tsx:48`).
- **Repro:** Crear invitación, esperar > `expiresAt` (24h), ir a `/sign-up?inviteToken=…&email=…`, completar registro → se acepta y une al team aunque el link debería estar caducado.
- **Impacto:** Un atacante con un token filtrado (logs, captura email leak) puede unirse a un team meses después.
- **Fix:** Añadir `gt(invitations.expiresAt, new Date())` al `and(...)` en línea 165-172.
- **Esfuerzo:** 2 min.

### B4. `NuevaFacturaForm` no pasa props requeridas a `ClienteSection` — Notas de Crédito/Débito rotas
- **File:** `app/(dashboard)/dashboard/facturas/nueva/NuevaFacturaForm.tsx:544-563`
- **Evidence:** `npx tsc --noEmit` reporta:
  ```
  app/(dashboard)/dashboard/facturas/nueva/NuevaFacturaForm.tsx(581,14): error TS2740:
  Type ... is missing the following properties from type 'Props':
  codigoModificacion, setCodigoModificacion, fechaNcfModificado, setFechaNcfModificado, and 2 more.
  ```
- **Behavior:** `ClienteSection.tsx:34-41` declara como **obligatorias**: `codigoModificacion`, `setCodigoModificacion`, `fechaNcfModificado`, `setFechaNcfModificado`, `tipoIngresos`, `setTipoIngresos`. El padre no las pasa.
- **Impacto:**
  - El form compila (Next.js permite errores TS en dev), pero en `tipoEcf === '33' | '34'` el bloque "Código de modificación" y "Fecha del NCF modificado" recibe `undefined`. El usuario ve un Select vacío, no puede elegir motivo de NC/ND.
  - El payload enviado a `/api/ecf/emitir` no incluye `codigoModificacion`/`fechaNcfModificado` → DGII rechaza el comprobante o ecf-api 422.
- **Fix:** Agregar 6 estados al `NuevaFacturaForm` (`codigoModificacion`, `fechaNcfModificado`, `tipoIngresos` y sus setters), inicializarlos desde `initialData?.codigoModificacion` etc., y pasarlos a `ClienteSection` en líneas 544-563.
- **Esfuerzo:** 15 min.

## C) High-impact UX issues (P1)

### C1. Errores en INGLÉS en `signIn`/`signUp` (mixto con UI 100 % en español)
- **File:** `app/(login)/actions.ts:91, 132, 150, 193, 203`
- **Strings:** `"Invalid email or password. Please try again."`, `"Failed to create user. Please try again."`, `"Invalid or expired invitation."`, `"Failed to create team. Please try again."`, `"Current password is incorrect."`, etc.
- **Fix:** Traducir todas. Patrón sugerido: `"Email o contraseña incorrectos."`, `"No se pudo crear el usuario."`, `"Invitación inválida o expirada."`, etc.
- **Esfuerzo:** 10 min.

### C2. `signIn`/`signUp` actions devuelven la `password` en el state (visible en client)
- **File:** `app/(login)/actions.ts:91-94, 131-135, 150-154, 192-194`
- **Behavior:** Cuando la validación falla, `return { error, email, password }` — el `useActionState` deja el password en `state.password`, que en `login.tsx:82` se usa para repoblar `defaultValue={state.password ?? ''}`. Mejor UX pero la contraseña viaja por el wire de la response RSC.
- **Fix:** Eliminar `password` del payload de retorno; `defaultValue` solo para email.
- **Esfuerzo:** 5 min.

### C3. `/api/webhooks` POST no valida URL ni esquema (z.object)
- **File:** `app/api/webhooks/route.ts:17-31`
- **Issue:** Acepta `{nombre, url, eventos}` sin Zod. URL puede ser `file://`, `javascript:`, `internal-host:port`, lo que abre riesgo SSRF cuando el cron/worker dispare el webhook.
- **Fix:** Schema Zod con `z.string().url().startsWith('https://')` y validación de allowlist de eventos.
- **Esfuerzo:** 10 min.

### C4. `/api/webhooks` GET devuelve `secret` en la lista
- **File:** `app/api/webhooks/route.ts:9-14`
- **Behavior:** `db.select().from(outboundWebhooks)` devuelve todos los campos incluyendo el `secret`. El cliente lo necesita SOLO para mostrar "copiar" — el UI ya lo expone como botón.
- **Issue:** En logs/capturas/proxies puede filtrarse.
- **Fix:** Devolver `secret` sólo en `POST` (creación). En GET incluir un `hasSecret: true` o un campo `secretPrefix` truncado. Para "copiar" añadir endpoint dedicado `POST /api/webhooks/[id]/reveal-secret` que requiera reautenticación reciente.
- **Esfuerzo:** 20 min.

### C5. `/dashboard/notas-credito` carga 500 docs y filtra en JS
- **File:** `app/(dashboard)/dashboard/notas-credito/page.tsx:24-25`
- **Code:**
  ```ts
  const allDocs = await getEcfDocuments(teamId, 500);
  const docs = allDocs.filter(d => d.tipoEcf === '34');
  ```
- **Issue:** Para teams activos con cientos de facturas tipo 31/32, se descargan datos innecesarios y siempre se limita a las primeras 500 (puede ocultar NCs reales si el team tiene > 500 facturas mixtas).
- **Fix:** Crear `getEcfDocuments(teamId, limit, { tipoEcf: '34' })` o filtro WHERE en query.
- **Esfuerzo:** 15 min.

### C6. `/admin/usuarios` sin paginación, búsqueda, ni filtro (hard limit 500)
- **File:** `app/admin/usuarios/page.tsx:6-18`
- **Issue:** Cuando la plataforma tenga > 500 usuarios, simplemente se cortan los más antiguos sin aviso. Tampoco hay buscador.
- **Fix:** Añadir paginación (offset/limit con `?page=N`), buscador `?q=` y filtro por `platformRole`/`emailVerified`/`twoFactorEnabled`.
- **Esfuerzo:** 45 min.

### C7. Login form no muestra avisos de bloqueo de cuenta tras N intentos
- **File:** `app/(login)/actions.ts:55-60`
- **Behavior:** `rateLimit('login:'+ip, 10, 60_000)`. Bloquea por IP, no por cuenta. Un atacante con muchas IPs puede credential-stuffing hasta forever. Tampoco hay backoff exponencial ni captcha.
- **Fix:** Añadir rate-limit por `email` también (`rateLimit('login:'+email, 5, 60_000)`); idealmente Turnstile/hCaptcha tras 3 fallos.
- **Esfuerzo:** 30 min.

### C8. Security: 2FA QR usa servicio EXTERNO (`api.qrserver.com`)
- **File:** `app/(dashboard)/dashboard/security/page.tsx:148-156`
- **Issue:** El `otpauth://` URI (que contiene el secret TOTP) se manda como query string a `api.qrserver.com`. Privacidad y dependencia externa. Si el servicio cae, el QR no se ve.
- **Fix:** Usar `qrcode` (ya en deps según `route.ts`) en el servidor; `/api/auth/2fa/setup` devuelve el PNG data URL.
- **Esfuerzo:** 15 min.

### C9. Confirmación destructiva usa `window.confirm()` nativo
- **Files:**
  - `app/admin/empresas/[id]/confirm-button.tsx:20`
  - `app/(dashboard)/dashboard/api-keys/_page-client.tsx:46`
  - `app/(dashboard)/dashboard/webhooks/_page-client.tsx:52`
  - `app/(dashboard)/dashboard/facturas/page.tsx:75`
- **Issue:** Diálogo nativo del navegador (estilo OS), no es accesible, no se puede traducir el botón "OK/Cancel", no se ve bien en mobile.
- **Fix:** Usar `<Dialog>` de shadcn como ya hace `clientes/_page-client.tsx:285-309`.
- **Esfuerzo:** 10 min por archivo (4 archivos = 40 min).

### C10. `alert()` para errores en operaciones de Equipo
- **File:** `app/(dashboard)/dashboard/equipo/page.tsx:211, 231`
- **Behavior:** Tras error al cancelar invitación / cambiar rol → `alert(e.message)`. Inconsistente con el resto (toast / banner inline).
- **Fix:** Reemplazar con `toast.error(...)` (sonner ya importado en otros sitios) o `setRemoveError` ya existente.
- **Esfuerzo:** 5 min.

### C11. Configuración sube imágenes en base64 a la BD (1 MB cada)
- **File:** `app/(dashboard)/dashboard/configuracion/page.tsx:49-57`, `app/api/equipo/perfil/route.ts:12,25-26`
- **Behavior:** El logo/firma se serializa como `data:image/...;base64,...` y se guarda en columna `teams.logo`/`teams.firma`. Cada select de equipo carga 1 MB extra. Sin CDN.
- **Fix:** Subir a Vercel Blob (`@vercel/blob`) o S3; guardar sólo la URL. Reduce el peso del select de teams en > 90 %.
- **Esfuerzo:** 1.5 h.

### C12. Validación de tamaño de imagen con `alert()`
- **File:** `app/(dashboard)/dashboard/configuracion/page.tsx:52`
- **Fix:** `toast.error('Imagen demasiado grande (máx 800 KB).')`.

1. **Body sin zod** (≈ 18 endpoints listados arriba) — sólo validación manual de campos clave. Patrón sugerido: definir `schemas/` por recurso y `safeParse`.
2. **Rate limiting esporádico:** sólo `login`, `invite-accept`, `habilitacion_sign`, `cert_upload`. Faltan: `forgot-password`, `send-verification`, `facturas/[id]/email`, `webhooks` POST.
3. **Mensajes de error genéricos en inglés-medio-español** (mezcla `"Error interno"` vs `"Error: ..."`). Consolidar.
4. **No hay validación de `request.headers.get('content-type')` antes de `req.json()`** en la mayoría — un POST con `Content-Type: text/plain` rompe con stacktrace en el log.
