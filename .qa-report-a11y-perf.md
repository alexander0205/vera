# EmiteDO — Accessibility (WCAG 2.1 AA) & Performance Audit

**Branch:** `feature/lite-version`
**Auditor:** Read-only static code review (axe/pa11y not installed; would require deps)
**Scope:** Sign-in, dashboard pages, admin panel, layouts
**Date:** 2026-05-12

---

## EXECUTIVE SUMMARY

EmiteDO ships a useful Spanish-localized invoicing UI on Next.js 15.6 canary with PPR, but it has **systemic WCAG 2.1 AA violations** centered on three patterns:

1. **Custom modals built from raw divs** — none have `role="dialog"`, `aria-modal`, focus trap, focus return, or labelled-by. This is the single biggest a11y debt: ~6 modal sites (facturas list, habilitacion, ecf-tabs detail, custom dialogs).
2. **Low-contrast text-gray-400 used as primary text/UI color** — 332 occurrences. On `#fff` background, `text-gray-400` (`#9ca3af`) yields a 2.85:1 ratio — fails WCAG 1.4.3 (4.5:1).
3. **No skip-to-content link** and no `<main>` landmark labeling, fail SC 2.4.1 (Bypass Blocks).

On performance the biggest hits are: (a) `app/(dashboard)/dashboard/layout.tsx` is a 707-line `'use client'` root layout that re-fetches `/api/user` + `/api/empresa/list` on every `pathname` change and on every tab-visibility event, (b) `app/(dashboard)/dashboard/habilitacion/page.tsx` is **3,301 lines** in a single client component with raw `<img>` tags for tutorial screenshots, and (c) zero CSP / security headers, zero error tracking (Sentry/PostHog).

## E) Screen Reader Experience Predictions

Walking the **`/dashboard/facturas`** page with NVDA/VoiceOver:

1. **Top:** Lands on hamburger (no label → "button" with no name on mobile).
2. **Sidebar:** "Nueva Factura, link"; nav groups read as "Ingresos, button, collapsed/expanded" — but no `aria-expanded` → state lost. Sub-items read as list of links.
3. **Main h1:** "Facturas, heading level 1" — good.
4. **CSV button:** "CSV, button" — good.
5. **Search input:** "edit blank" — **bad** (no label).
6. **Estado select:** "Todos los estados, listbox" — good.
7. **Bulk action when something is selected:** Banner is not announced (no `aria-live`).
8. **Table:** Headers read as plain text since `scope` is missing — screen reader can't associate cells.
9. **Email modal opens:** Focus does **not** move to the modal — screen reader continues on the previous link. User has no idea a modal opened.
10. **Inside modal:** No `role=dialog` → reads as "Enviar factura por email, heading 2" mid-page. Closing with Esc doesn't work.

Walking **`/sign-in`**:

1. h1 — there isn't one. EmiteDO logo is a `<span>` — no heading. Screen reader has no top-level landmark.
2. Email input — labelled "Email" ✓.
3. Password — labelled "Contraseña" ✓. Show/hide button has `aria-label` ✓ but `tabIndex={-1}` so keyboard users can't reach it.
4. Submit error banner — **not announced** because no `role="alert"`.

## G) Server vs Client Component Opportunities

`app/(dashboard)/dashboard/layout.tsx` is **`'use client'`** at the top of the dashboard tree. This is the single highest-leverage refactor in the app.

Consequences:
- All descendants run on the client. SWR is set up in the root layout (`app/layout.tsx`) but the dashboard sub-layout doesn't use SWR for user/empresa data — it does a manual `fetch` in `useEffect`, ignoring the SWR `fallback`. Lines 634-651.
- Three re-fetch sites: initial mount, every `pathname` change (line 651), and every tab-visibility change (line 658). On a typical session this fires `/api/user` + `/api/empresa/list` 5–20× per minute.
- Sidebar nav config (`GROUPS`, `TOP_ITEMS`) is static — could be in a server file. Only the dropdowns, mobile toggle, and active-route highlighting need client.

**Refactor:** split into `DashboardLayoutServer` (data fetch via `getUser`/`getUserTeams` server functions) + small client islands for `CompanySwitcher`, `ProfileDropdown`, and the mobile sidebar toggle. Re-use the SWR fallback already wired in `app/layout.tsx`.

Other server-able candidates:

| File | Why client today | Server-able? |
|---|---|---|
| `app/(dashboard)/dashboard/facturas/page.tsx` | Search/filter UI | Filters can stay client but initial data + pagination would benefit from `searchParams`-driven server rendering |
| `app/admin/usuarios/page.tsx` | Already server ✓ | — |
| `app/(dashboard)/dashboard/empresas/page.tsx` | Wraps `EmpresasClient` | The list could be passed from server (already is); the Crear-empresa Dialog is the only thing needing client |
| `app/(dashboard)/dashboard/clientes/page.tsx` | Just renders `ClientesClient` | Could pre-fetch the first page server-side and hydrate the client list |
| `app/(dashboard)/dashboard/habilitacion/page.tsx` | 3301-line `'use client'` | Tutorial content is mostly static — can be 80% server-rendered with islands for the interactive modals |
